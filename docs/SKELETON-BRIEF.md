# 스켈레톤 단계 작업 안내

# 0. 문서 정보
- 목적: 구현체와 함수 스켈레톤 코드 구성 단계를 새 Claude Code 세션에서 바로 시작하기 위한 정보

  - 이 문서
  - `docs/ARCHITECTURE.md`

- 시작 요청 예: "docs/SKELETON-BRIEF.md를 읽고 스켈레톤 단계 계획 제시"

# 2. 스켈레톤 단계의 범위
- 목표: 헤더별 총괄 구현체와 공개 함수의 뼈대 코드
- 포함
  - workspace, crate, 디렉토리 생성
  - 총괄 구현체의 영문 이름 확정
  - 헤더별 공개 인터페이스 검토와 확정
  - 본문 없는 구현체와 함수 선언 작성
    - 함수 본문: 요약 한 줄의 미구현 표시와 단계별 동작 주석
    - 단계 주석: 스켈레톤 단계 한정의 주석 예외
- 제외
  - 함수 본문 구현
  - 헤더 안 세부 모듈 구성

# 3. 재구현의 전제
- 작업 위치: `restructure` 브랜치
- 기존 코드: 전부 삭제 후 재구현

- 하네스: 새 구조에 맞지 않는 부분 재구성

# 5. 스켈레톤 구성 기준

| 대상 | 자리 | 내용 |
|---|---|---|
| 서비스 관리의 총괄 구현체 | 서비스 관리 crate의 `lib.rs` | 메인 서비스 |
| 헤더의 총괄 구현체 | 헤더 디렉토리의 `mod.rs` | 헤더 이름의 구현체 하나 |
| 로그 관리의 총괄 구현체 | 로그 crate의 `lib.rs` | 로그 관리 구현체 하나 |
| UI의 총괄 구현체 | `user/ui/OS` 최상위 | UI 구현체 하나 |
| UI 세 기능의 총괄 구현체 | `user/ui/OS/기능` | 기능별 구현체 하나 |
| 메인 서비스 메시지 | 두 영역 `protocol`의 `service` 모듈 | 메시지와 전달 수단 |
| 세부 기능 | 헤더 디렉토리 안 모듈 파일 | 스켈레톤 단계 제외 |

- 메인 서비스의 이름
  - 시스템 영역: VPN Helper 서비스
  - 사용자 영역: VPN 앱 서비스

- `docs/FEATURES.md`의 기능 항목: 헤더의 뜻을 보여 주는 대표 인터페이스 예시
  - 파일이나 구현체 단위가 아님
- 세부 기능의 형태: 구현체와 함수 중 구성이 단순한 쪽 우선
  - 규모가 커지면 구현체로 변경
- 기존 workspace 설정
  - Rust edition 2024
  - `unsafe_code` 금지
  - clippy `all`·`pedantic` 금지 수준
  - 유지 여부: 유지
- 기능의 공개 함수: `new`, `init`, `push`, `run`
  - `init`: 한 번만 하는 사전 준비
  - `run`: 반복되는 작업 전부, 절차별 내부 함수 호출만
  - 준비할 것이 없는 기능: `init` 없음
- UI 준비 함수의 이름: Swift `setUp`, C# `Initialize`

# 6. 헤더 역할 합의

## 시스템 영역

| 헤더 | 합의 내용 |
|---|---|
| VPN Helper 서비스 | 기능 생성과 조합, 메인 루프 관리, 서비스 시작과 종료의 경계 |
| VPN 연결 관리 | 세션 여럿 보유, 세션의 연결·재연결·종료, 세션 교체 절차 수행 |
| 네트워크 관리 | 터널 주소·route·DNS 설정, 예외 경로의 평가와 반영, 경로·인터페이스 변화 감지 |
| 앱 연동 관리 | 요청 채널의 연결·요청 수신·응답 송신, 전파 채널의 상태 변화 전파, 로그 채널의 로그 줄 송신, 요청 분석 |
| Helper 운영 상태 관리 | 이전 Helper가 남긴 기록의 확인과 보고, 기록의 저장과 삭제 |
| 로그 관리 | 로그의 형식, 쓰기, 회전 수행 |
| 업데이트 관리 | 업데이트 준비, 설치 |

- 시스템 영역의 성격: 요청 실행, 자기 자원의 사실 관찰, 관찰한 네트워크 사실에 따른 예외 경로 적용
- 이전 Helper가 남긴 것의 정리: 그것을 만든 기능
- VPN 연결 관리
  - 세션 수 제한: 없음
  - 세션 교체 여부와 시점: 사용자 영역 결정
  - 시스템 전체에 적용되는 터널: 동시에 하나
- 앱 연동 관리
  - 상대 확인: 채널 연결의 협상 단계
  - 전파 채널의 전파 대상: VPN 연결 상태의 변화, 예외 경로 상태의 변화
- 로그 관리
  - 다른 헤더: 로그 인터페이스 호출
- 업데이트 관리
  - 설치 파일 검증: 헤더 안 함수 단위

## 사용자 영역

| 헤더 | 합의 내용 |
|---|---|
| VPN 앱 서비스 | 기능 생성과 조합, 메인 루프 관리, 서비스 시작과 종료의 경계 |
| VPN 연결 제어 | 연결·재연결·종료 제어, 연결에 대한 판정 |
| 연결 정책 관리 | 연결 스케줄, 유휴 상태 |
| 인증 관리 | VPN 계정, OTP와 Google 계정 연결 |
| Helper 연동 관리 | 요청 채널, 전파 채널, 로그 채널, 앱 실행 시 Helper 기동 |
| 설정 관리 | 설정 로드, 외부 설정 로드, 저장, 앱 상태 유지 |
| 로그 관리 | 로그의 형식, 쓰기, 회전 수행 |
| 업데이트 관리 | 업데이트 확인, 수행 |
| UI | 메뉴바(트레이), 설정창, 알림 |

- 사용자 영역의 성격: 연결 판정
- VPN 연결 제어
  - 연결 판정의 유일한 자리
  - 사용자 의사, 스케줄, 유휴 규칙을 조합한 판정 담당
  - 사전 재연결 시각의 감시 담당
- 연결 정책 관리
  - 스케줄, 유휴 상태: 각각 별개 인터페이스
  - 유휴 상태: 자리비움과 잠자기 감지 포함
- 인증 관리
  - 비밀값 보관 담당
- Helper 연동 관리
  - Helper 서비스 등록과 자동 시작 설정: 설치 패키지 담당
  - 기동 호출 시점: VPN 앱 서비스 결정
  - 승인 대기 중 기동 재시도 담당
- UI
  - 역할: 표시와 입력 한정
  - 진입점과 UI 외 Swift·C# 코드: 없음
  - UI 외 헤더의 UI 참조: 없음
    - 알림: 알릴 일만 내놓는 방식
  - 번역 리소스 사용처: UI 한정

## 두 영역 공통
- 전체 흐름: 동기, 절차가 코드에 순서대로 드러나는 형태
- 기능의 독립: 기능 사이 참조 없음
  - 의존이 필요해지는 경우: 사용자 검토 요청
- 기능에 필요한 관찰과 주기 작업: 해당 기능이 수행
- 메인 서비스: 메시지 종류별 고정 규칙으로 기능에 작업 전달, 판정과 기능 상태의 직접 관리 없음
- 메인 루프: 메시지가 들어오면 전달, 그 밖에는 대기
- 메시지와 작업: 처리에 필요한 내용을 모두 담은 요청 단위
- 기능의 실행: 기능마다 전용 스레드와 작업 큐
- 기능의 결과: 메인 서비스 메시지로 전달, 다른 기능의 작업으로의 변환은 메인 서비스 담당
- 기능 사이 전달 수단: 메시지와 작업 한정
  - 함수를 인자로 넘기는 방식 없음
- 기능의 공개 함수: 동기 함수
- 절차: 시작부터 끝까지 내부 함수 하나로 수행
- 절차의 진행 위치: 상태로 저장하지 않음
- 절차의 대기: 기다리는 동안 자기 작업 큐를 읽어 다른 작업 처리
- 시각에 따른 작업: 실행 함수가 그 시각까지만 작업을 기다리는 방식
  - 별도 타이머 스레드 없음
- 기능의 종료: 중지 작업 전달, 스레드 종료로 확인
  - 종료 요청·확인 전용 함수 없음
- 비동기: 유보, 실행 함수의 전환 여부는 구현 단계 결정
- Helper 서비스: 상시 실행
- 앱 미실행 중 재연결: 없음
- 프로토콜 구조: `common/base`의 `protocol`
- 프로토콜 구현체: 두 영역의 `protocol` crate

# 7. 구현 단계로 넘긴 사항
- 구조에 관한 항목: `docs/ARCHITECTURE.md` 10절
- 중지 쪽 시간 제한의 필요 여부
  - 함께 재검토: `decisions.md`의 의도된 Helper 재시작 대상, 업데이트 작업의 멈춤 감시 제외
- 설치 프로그램이 Helper를 중지시킬 때의 설치 결과 기록
- 재시도의 간격과 횟수
  - 포함: 승인 대기 중 Helper 기동 재시도
- Rust 통로의 `unsafe_code` 예외
- 로그인 시 열기의 설정 항목 전환
- 기존 state.json 값의 이전 여부
- Helper 재연결 시 예외 규칙 재전송
- 예외 규칙 조회의 요청 주체와 시점
- 설정 관리의 답 없는 요청 처리
- 앱 연결 수락 전 정리 범위
- 설치 거절 시 앱 다시 열기 준비의 원복
- crate 사이 순환 의존: 불가
- 묶음 사이 의존이 필요해지는 경우: 사용자 검토 요청

# 8. 기존 코드 참조 위치
- 기준: main 브랜치, `docs/SPEC.md` 1.1의 구성 요소 표
- 용도: 인터페이스 검토 때 기존 동작 확인

| 기존 구성 요소 | 기존 자리 | 새 자리 |

| 런타임 | `components/runtime` | `user/service`, `user/connection`, `user/log` |

  - 대상: `app_internal`, `helper_internal`

# 9. 하네스와 문서의 재검토 대상

# 10. 설계 단계에서 확인된 진행 기준
- 단계 범위: 해당 단계에서 정할 것만 논의
  - 설계 단계에서 제외했던 것: 세부 동작, 구현 방식
- 명칭
  - 동작 표현이 아닌 기능 명칭 사용
  - 짝을 이루는 요소의 표현 통일
  - 명칭 뒤 괄호 부연 설명 미표시
- 헤더 크기: 같은 단계의 다른 헤더보다 지나치게 세부적인 헤더 금지
- 문서와 디렉토리: 단계 일치
