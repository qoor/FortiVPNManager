# 스켈레톤 단계 작업 안내

# 0. 문서 정보
- 목적: 구현체와 함수 스켈레톤 코드 구성 단계를 새 Claude Code 세션에서 바로 시작하기 위한 정보
- 읽는 순서
  - 이 문서
  - `docs/ARCHITECTURE.md`
  - `docs/FEATURES.md`
- 시작 요청 예: "docs/SKELETON-BRIEF.md를 읽고 스켈레톤 단계 계획 제시"

# 1. 현재 상태

| 항목 | 상태 |
|---|---|
| 기능 구성, 아키텍처, 디렉토리 | 확정 |
| 총괄 구현체의 영문 이름 | 미정 |
| 공개 인터페이스 | 미검토 |
| 스켈레톤 코드 | 미착수 |
| SPEC 재작성 | 미착수 |
| 하네스 재구성 | 미착수 |

- 작업 브랜치: `restructure`
  - 기존 소스 `components`: 삭제 상태
- 기존 코드: main 브랜치에 보존
  - 재구현 완료 후: 레거시 브랜치로 유지

# 2. 스켈레톤 단계의 범위
- 목표: 헤더별 총괄 구현체와 공개 함수의 뼈대 코드
- 포함
  - workspace, crate, 디렉토리 생성
  - 총괄 구현체의 영문 이름 확정
  - 헤더별 공개 인터페이스 검토와 확정
  - 본문 없는 구현체와 함수 서명 작성
- 제외
  - 함수 본문 구현
  - 헤더 안 세부 모듈 구성

# 3. 재구현의 전제
- 작업 위치: `restructure` 브랜치
- 기존 코드: 전부 삭제 후 재구현
- 하위호환: 전부 폐기
- 유지 대상
  - UI의 전체 디자인, 구성, 배치
  - 빌드 스크립트의 틀
  - 빌드 방식
- 문서: 새 구조에 맞춰 재작성
- 하네스: 새 구조에 맞지 않는 부분 재구성

# 4. 작업 순서 제안
- 사용자 승인 전 상태의 제안
- 순서
  - workspace와 crate 뼈대 생성
  - 총괄 구현체의 영문 이름 제안과 승인
  - 헤더별 공개 인터페이스 검토
    - 출발점: `docs/FEATURES.md`의 기능 항목
  - 스켈레톤 코드 작성
  - 두 OS 빌드 확인
- 헤더별 공개 인터페이스 검토 단위: 헤더 하나씩 제시

# 5. 스켈레톤 구성 기준

| 대상 | 자리 | 내용 |
|---|---|---|
| 서비스 관리의 총괄 구현체 | 서비스 관리 crate의 `lib.rs` | 메인 서비스 |
| 헤더의 총괄 구현체 | 헤더 디렉토리의 `mod.rs` | 헤더 이름의 구현체 하나 |
| 로그 관리의 총괄 구현체 | 로그 crate의 `lib.rs` | 로그 관리 구현체 하나 |
| UI 세 기능의 총괄 구현체 | `user/ui/OS/기능` | 기능별 구현체 하나 |
| 세부 기능 | 헤더 디렉토리 안 모듈 파일 | 스켈레톤 단계 제외 |

- 메인 서비스의 이름
  - 시스템 영역: VPN Helper 서비스
  - 사용자 영역: VPN 앱 서비스

- `docs/FEATURES.md`의 기능 항목: 헤더의 뜻을 보여 주는 대표 인터페이스 예시
  - 파일이나 구현체 단위가 아님
- 세부 기능의 형태: 구현체와 함수 중 구성이 단순한 쪽 우선
  - 규모가 커지면 구현체로 변경
- 기존 workspace 설정
  - Rust edition 2024
  - `unsafe_code` 금지
  - clippy `all`·`pedantic` 금지 수준
  - 유지 여부: 계획에서 확인

# 6. 헤더 역할 합의

## 시스템 영역

| 헤더 | 합의 내용 |
|---|---|
| VPN Helper 서비스 | 기능 생성과 조합, 메인 루프 관리, 서비스 시작과 종료의 경계 |
| VPN 연결 관리 | 세션 여럿 보유, 세션의 연결·재연결·종료, 세션 교체 절차 수행 |
| 네트워크 관리 | 터널 주소·route·DNS 설정, 예외 경로의 평가와 반영, 경로·인터페이스 변화 감지 |
| 앱 연동 관리 | 요청 채널의 연결·요청 수신·응답 송신, 전파 채널의 VPN 연결 상태 변화 전파, 요청 분석 |
| Helper 운영 상태 관리 | 운영 상태 확인, 저장, 복구 |
| 로그 관리 | 로그의 형식, 쓰기, 회전 수행 |
| 업데이트 관리 | 업데이트 설치 |

- 시스템 영역의 성격: 요청 실행, 자기 자원의 사실 관찰, 관찰한 네트워크 사실에 따른 예외 경로 적용
- VPN 연결 관리
  - 세션 수 제한: 없음
  - 세션 교체 여부와 시점: 사용자 영역 결정
  - 시스템 전체에 적용되는 터널: 동시에 하나
- 앱 연동 관리
  - 상대 확인: 채널 연결의 협상 단계
  - 전파 채널의 전파 대상: Helper가 관리하는 VPN 연결 상태의 변화 한정
- 로그 관리
  - 다른 헤더: 로그 인터페이스 호출
- 업데이트 관리
  - 설치 파일 검증: 헤더 안 함수 단위

## 사용자 영역

| 헤더 | 합의 내용 |
|---|---|
| VPN 앱 서비스 | 기능 생성과 조합, 메인 루프 관리, 서비스 시작과 종료의 경계 |
| VPN 연결 제어 | 연결·재연결·종료 제어, 연결에 대한 판정 |
| 연결 정책 관리 | 연결 스케줄, 유휴 상태 |
| 인증 관리 | VPN 계정, OTP와 Google 계정 연결 |
| Helper 연동 관리 | 요청 채널, 전파 채널, 앱 실행 시 Helper 기동 |
| 설정 관리 | 설정 로드, 가져오기, 저장, 앱 상태 유지 |
| 로그 관리 | 로그의 형식, 쓰기, 회전 수행 |
| 업데이트 관리 | 업데이트 확인, 수행 |
| UI | 메뉴바(트레이), 설정창, 알림 |

- 사용자 영역의 성격: 연결 판정
- VPN 연결 제어
  - 연결 판정의 유일한 자리
  - 사용자 의사, 스케줄, 유휴 규칙을 조합한 판정 담당
- 연결 정책 관리
  - 스케줄, 유휴 상태: 각각 별개 인터페이스
  - 유휴 상태: 자리비움과 잠자기 감지 포함
- Helper 연동 관리
  - Helper 서비스 등록과 자동 시작 설정: 설치 패키지 담당
  - 기동 호출 시점: VPN 앱 서비스 결정
- UI
  - 역할: 표시와 입력 한정
  - UI 외 헤더의 UI 참조: 없음
    - 알림: 알릴 일만 내놓는 방식
  - 번역 리소스 사용처: UI 한정

## 두 영역 공통
- 전체 흐름: 동기, 절차가 코드에 순서대로 드러나는 형태
- 기능의 독립: 기능 사이 참조 없음
  - 의존이 필요해지는 경우: 사용자 검토 요청
- 기능에 필요한 관찰과 주기 작업: 해당 기능이 수행
- 메인 서비스: 큐에서 꺼낸 작업을 대상 기능에 전달, 기능 상태의 직접 관리 없음
- 메인 루프: 작업 큐에 작업이 들어올 때 한 바퀴 수행, 그 밖에는 대기
- 작업 큐 항목: 대상 기능과 작업 내용
- 기능이 큐에 넣는 작업: 자기 앞 작업 한정
- 기능의 결과: 메인 서비스에 전달, 다른 기능 앞 작업으로의 변환은 메인 서비스 담당
- 기능의 공개 함수: 동기 함수
- 절차: 시작부터 끝까지 동기 함수 하나로 수행
- 절차의 진행 위치: 상태로 저장하지 않음
- 비동기의 범위: 앱 전체를 오래 멈추게 하는 I/O와 타임아웃 관리 한정
- 비동기 작업과 메인 루프 사이의 전달: 작업 큐 한정
- Helper 서비스: 상시 실행
- 앱 미실행 중 재연결: 없음
- 프로토콜 구조: `common/base`의 `protocol`
- 프로토콜 구현체: 두 영역의 `protocol` crate

# 7. 미확정 사항

| 항목 | 설계 단계의 권장안 |
|---|---|
| 메인 서비스의 연결 판정 여부 | 판정 없이 기능 연결만 |
| 앱 채널이 끊겼을 때 기존 연결의 처리 | 고정 규칙으로 정리 |
| Helper와 OpenConnect 라이브러리의 관계 | Helper 하나에 라이브러리 하나, 그 안에 세션 객체 여럿 |
| OS API의 OS별 모듈을 쓰는 쪽에 내주는 방식 | 없음 |
| 진입점도 UI도 아닌 Swift·C# 코드의 필요 여부 | 없음 |
| 최상위 C# 프로젝트의 소스 경로 지정과 중간 산출물 분리 | 없음 |
| 설정창 로그 화면의 Helper 쪽 VPN 로그 표시 방법 | 없음 |
| 예외 경로 적용 실패를 앱에 알리는 경로 | 없음 |
| 절차 도중의 취소 방법 | 없음 |

- 권장안: 사용자 승인 전 상태
- crate 사이 순환 의존: 불가
  - 두 묶음이 서로 필요할 때: 묶음의 crate 경계 재검토
- Windows 제약: Wintun 로그 콜백 대상이 프로세스 전체에 포인터 하나
  - 근거: `.claude/rules/constraints.md`
  - 영향: 두 세션이 겹치는 구간의 처리 주체 지정 필요

# 8. 기존 코드 참조 위치
- 기준: main 브랜치, `docs/SPEC.md` 1.1의 구성 요소 표
- 용도: 인터페이스 검토 때 기존 동작 확인
- 대응 관계: 착수 전 확인 필요

| 기존 구성 요소 | 기존 자리 | 새 자리 |
|---|---|---|
| 판단 코어 | `components/core` | `user/connection`, `user/service` |
| 런타임 | `components/runtime` | `user/service`, `user/connection`, `user/log` |
| 공통 계약 | `components/contract` | `common/base` |
| backend adapter | `components/backend-adapter` | `system/openconnect`, `system/connection` |
| Helper 공통 모듈 | `components/helper/core` | `system/service`, `system/connection`, `system/protocol`, `system/log` |
| Helper OS 영역 | `components/helper/macos`, `components/helper/windows` | `system/helper`, `common/os-api` |
| OS API | `components/os-api/macos`, `components/os-api/windows` | `common/os-api` |
| OS 연동 | `components/os-integration` | `user/app`, `user/protocol`, `common/os-api` |
| UI | `components/ui` | `user/ui`, `user/resources` |
| 설치 패키지, 프로젝트 정의 | `packaging` | `packaging`, 저장소 최상위 |

- 기존 공통 계약의 한 영역 전용 구조: 공용이 아닌 해당 영역 crate로 이동
  - 대상: `app_internal`, `helper_internal`

# 9. 하네스와 문서의 재검토 대상
- `.claude/rules`의 적용 경로: `components/**` 기준
  - 새 디렉토리 `system`, `user`, `common`에 맞춘 변경 필요
- `.claude/rules/decisions.md`: 하위호환 폐기로 사유가 사라지는 결정 재검토
  - 재검토 시 해당 결정의 원래 요구사항을 사용자에게 재제기
  - 예: 앱과 Helper 통신 방식 유지 결정, 이전·다음 빌드의 저장 데이터 형식 유지
- Helper 서비스 등록 주체 변경: 앱에서 설치 패키지로
  - 관련 결정과 제약 재검토 필요
- `docs/SPEC.md`: 새 구조에 맞춰 재작성
- `docs/DESIGN.md`: 갱신과 참조 금지 문서
- 스크립트의 경로: `Makefile`, `scripts`, `packaging`의 스크립트가 가리키는 기존 디렉토리 변경 필요

# 10. 설계 단계에서 확인된 진행 기준
- 단계 범위: 해당 단계에서 정할 것만 논의
  - 설계 단계에서 제외했던 것: 세부 동작, 의존 방향, 구현 방식
- 명칭
  - 동작 표현이 아닌 기능 명칭 사용
  - 짝을 이루는 요소의 표현 통일
  - 명칭 뒤 괄호 부연 설명 미표시
- 헤더 크기: 같은 단계의 다른 헤더보다 지나치게 세부적인 헤더 금지
- 문서와 디렉토리: 단계 일치
